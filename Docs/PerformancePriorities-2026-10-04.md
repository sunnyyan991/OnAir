# 性能诊断与后续执行顺序

## 结论

优先优化**第二层高架规划所触发的广域建筑布局计算**，然后处理地图生成的不可分割步骤、建筑原始阴影模型和缓存分配。当前证据不支持优先减少车辆或降低画质。

本轮只加入观测计时，并对新增绿地源模型做材质合并。未修改原有高架路线、城市密度、摄像机范围、飞机高度、云影强度或随机窗户逻辑；下面的大项交给后续执行模型实施。

## 已测得的证据

独立 Unity 2022.3 验证工程，Main、固定种子 2409，180 个运行帧。记录在 `Art/Reviews/CityLife/validation.txt`，完整日志在工作区 `city-life-runtime.log`。

| 项目 | 结果 |
|---|---:|
| 请求进入 Play 到初始稳定帧 | 51.01 秒 |
| TerrainStreamer 首次同步 Refresh | 48,694 毫秒 |
| 其中第二层高架阶段 | 41,534 毫秒，约 85.3% |
| 地形面片阶段 | 1,573 毫秒 |
| 当前可见区域人口 / 实例阶段 | 2,882 毫秒 |
| 初始材质、网格上传阶段 | 1,098 毫秒 |
| 初始低层交通规划阶段 | 401 毫秒 |
| 驻留地图块 / 建筑实例 | 36 / 613 |
| Renderer（含阴影源）/ 像素对象 | 13,169 / 1,040 |
| 运行中的最长单步生成耗时 | 8.85 毫秒，population |
| 同步补图次数 / 缺失可见块 | 0 / 0 |
| 新增车辆逻辑 CPU 中位 / P95 / 最大值 | 0.047 / 0.095 / 0.816 毫秒 |

批处理 Editor 的帧时间中位 1.39ms、P95 11.59ms、最大 14.85ms，**不能换算为用户实际 Play 窗口的 FPS**；没有采集 GPU 时间，也没有做同条件“车辆关闭”的 GPU 对照。第一轮相同场景曾测到单帧 69.40ms，说明短样本最大帧波动明显，不能据第二轮声称已经消除卡顿。项目打开本身另有约 21 秒的 Editor 初始化，不包含在上表的 Play 启动计时内，也不能当作发布版游戏启动时间。

初始阶段计时按协程每次推进后的阶段名归类，含该阶段内部调用的其他计算；例如 upper highways 包含它请求的离屏人口计划。它能确定优先级，尚不能把 41.5 秒全部归因于某一个内层函数。

## 优先项 1：第二层高架与人口计划缓存（收益最明确）

入口：`Assets/Scripts/World/WorldUpperHighways.cs` 的 `PrepareRegion`；`ContinuousWorldLayout.BuildIncrementally` 的 upper highways 阶段；`WorldPopulationCache`。

现状：单个候选高架长达约 760 米。候选路线采样后，逐个请求覆盖区域的完整建筑计划，再遍历建筑占地验证净空。初始地图同步建立多个 tile，同时触及周边多个高架归属区。人口缓存仅保留 64 个 Region 对象；广域探索可能造成重复布局计算。**缓存抖动是源码支持的重点怀疑，尚未用命中计数单独证实。**

执行要求：

1. 先增加高架候选数、人口缓存命中 / 未命中、重复 Region 计算、净空检查次数、各自 CPU 时间计数，不再次盲等整场验证。
2. 使用稳定 `(seed, generatorVersion, rx, rz)` 区域键；在本次高架规划期间保留所需人口数据。避免区域对象因地理缓存清空而失去身份。
3. 将 prefab 尺寸、高度、临街面等整理为可重用只读元数据；对建筑占地建立空间索引，只检查高架附近建筑，不对每个路线采样点遍历整条走廊的全部建筑。
4. 保留候选顺序、随机流、地块选择和所有安全净空条件。先实现结果完全相同的缓存 / 索引优化，再评估分阶段启动。
5. 初步目标：该阶段 CPU 至少下降 50%。这是执行目标，不是已证明的收益；用多个固定种子报告实际结果。

## 优先项 2：把“预算协程”真正拆成小工作块

入口：`TerrainStreamer.Start/Refresh/Pump/Commit`、`ContinuousWorldLayout.Populate`。

`generationBudgetMs=6` 只在一次 MoveNext 返回后检查，单个 MoveNext 已测到 8.85ms，所以不能保证一帧最多花 6ms。Start 调用同步 Refresh，把所有初始 required 和一部分 wanted 一次建完；运行时若缺可见块，也会同步补建到完成。

执行要求：

- 拆分一个地块的一长串候选查询、实例化、窗口准备、材质和网格上传；分别计时，软目标单个工作块 ≤2ms。
- `Populate` 的背排 while 循环不像前排那样每轮检查预算，先补齐可中断边界；不能只把全局预算从 6 改成 3 而不拆长步骤。
- 启动使用加载状态展示真实进度；可见区域全部完成前不开始正常飞行，不把半张地图直接暴露给用户。
- 保持摄像机需求范围不变；按到达时间预取，不能通过少画地块换取表面帧率。
- 加载时可以等待，正常飞行期间需要统计并降低 EmergencyCompletions，避免其同步工作产生长帧。

## 优先项 3：建筑运行时层级与阴影源简化

入口：`PixelObjectView.Configure`、`DistantDetailShadows`、各建筑生成器。

当前像素楼不是“只渲染一张图”：实例化完整作者模型后，把所有原始 MeshRenderer 设为 ShadowsOnly，再添加像素片。当前场景仍有 13,169 个 Renderer。`DistantDetailShadows.Start` 只收集 ShadowCastingMode.On，小块作者网格转为 ShadowsOnly 后不在这个候选集合内。

执行要求：

- 离线生成精简的运行预制体：保留已烘焙像素、必要元数据和合并后的阴影网格，移除每扇窗、钢管、文字方块的运行时对象层级。
- 先合并完全等价的阴影几何，不先删细节。源模型仍留在美术制作区供再烘焙；不能丢失四面截图、窗户 ID、看板插槽和广告动画数据。
- 用白天不同太阳角度对比阴影，再测 Instantiate、Renderer 数与 GPU shadow pass 时间。
- 本轮五款绿地已经按材质合并原始几何，避免重复旧楼的层级成本。

## 优先项 4：减少生成过程的分配与整批缓存清空

入口：`ContinuousWorldLayout.Populate`、`ContinuousWorldPlan.TrimCaches/Dry`、`WorldPopulationCache`。

循环中的 LINQ Where/ToArray、反复 GetComponent、Rect 候选集合与整数样本字典都应测分配量。部分缓存到阈值直接 Clear，会使后续计算重新冷启动；目前没有 GC pause 采样，不能把所有掉帧都直接称为 GC。

执行要求：预编译规则与 prefab 元数据、复用候选缓冲区；缓存按路线 / 空间距离渐进淘汰，避免在同一帧全清；用 Unity Profiler 的 GC Alloc 和 GC 时间证明改善，目标稳态交通更新与常规空闲帧不产生可观分配。修改前后对相同种子比较建筑位置、类型与朝向。

## 优先项 5：云影 GPU 成本，等前四项明确后再做

入口：`Assets/Resources/PixelClouds/CloudShadowOverlay.shader`。

全屏 pass 对每个屏幕像素循环当前云片，最多数组容量 128；屏外云也可能在屏内投影，所以不能仅按云本体是否出屏裁掉它。当前没有 GPU profiler 数据，此项是待测候选，不是已证实的主要瓶颈。

优先研究屏幕投影包围盒 / 分区列表，以接收阴影区域剔除无关云片；保留连续透明度、太阳角度、三层高度、入场退场和阴影深度。不把“降低阴影分辨率 / 减少云数 / 缩短渐隐”当作默认优化。

## 交给执行模型的验收边界

每次只修改一个主要瓶颈。固定种子至少 2409、8102，加一段 Town 和 HeavyRain；比较同视角日夜截图、建筑布局哈希、高架路线点、云影渐显渐隐和车辆颜色 / 车灯。稳定飞行至少 60 秒，记录启动时间、P50/P95/P99、最长帧、GC、GPU、MissingVisibleTiles、EmergencyCompletions，并注明 Editor 或 Player。

启动验证设硬上限，长时间没有新证据就停止当前验证，读取日志 / 栈定位原因；不要通过重复等待或反复启动同一失败场景消耗时间。这个任务的性能大项尚未实施，不能将当前“功能检查通过”描述成“卡顿已修复”。
